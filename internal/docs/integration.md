# Integrating AWF

Use this guide to adopt AWF in a repository, connect its check to repository automation, update the pinned release, or repair an integration. If the repository already has an older AWF installation, follow `awf docs migrate` instead of the adoption steps below.

## Read before installation

The public launcher downloads its release's archive and checksums, verifies and caches the binary under `${XDG_CACHE_HOME:-$HOME/.cache}/awf/<version>/awf`, runs the requested command, and returns its exit status. Reading a guide this way does not touch the repository:

```sh
curl -fsSL https://github.com/hypnotox/agentic-workflows/releases/latest/download/awf.sh | bash -s -- docs integration
```

Alternatively, download an archive from the [latest release](https://github.com/hypnotox/agentic-workflows/releases/latest), extract `awf`, and run it directly. AWF supports Linux and macOS on amd64 and arm64.

The workflow skills require the [agentic-skills](https://github.com/hypnotox/agentic-skills) package. The workflows say where in a change a checkpoint belongs and which documents result, and name its methods, such as `agentic-brainstorming` and `agentic-reviewing`, for how to carry it out. AWF neither installs nor renders the package: install it in each agent harness the repository uses, following its README.

### An existing `docs/` tree

Every `.md` file recursively under `docs/`, including hidden directories and files AWF did not create, is part of the knowledge bundle that `check` validates. Each one except reserved `index.md` and `log.md` files needs leading YAML frontmatter with a non-empty `type` and `description` (`awf docs knowledge`). Installation itself succeeds regardless, and `render` and `resolve` do not validate these files, but `check` fails with one finding per non-conforming file until they are reconciled. Before relying on `check`, either:

- add the frontmatter to each document, which leaves its body untouched; or
- move documents that should not join the bundle out of `docs/`, repairing links to them.

There is no exclusion setting.

## Adopt a repository

1. Inspect existing agent and contributor instructions, any `docs/` tree, repository checks, hook scripts, CI, and the effective hook location (`git config --get core.hooksPath` in Git repositories). Check the fixed destinations listed below for existing files.
2. Keep useful repository instructions in author-owned `AGENTS.md` and current knowledge in `docs/topics/**/*.md`. AWF never creates or replaces `AGENTS.md` or `CLAUDE.md`; use `awf docs agents` to route agents to AWF in one sentence and to add optional Claude support.
3. From the repository root, install the fixed files with the latest release:

   ```sh
   curl -fsSL https://github.com/hypnotox/agentic-workflows/releases/latest/download/awf.sh | bash -s -- init
   ```

   To install a specific release, replace `latest/download` with `download/v<version>`. `init` performs the same generation as `render`, creates no descriptor or agent guide, and can be repeated. Afterwards, the generated `./awf` wrapper runs the pinned release.
4. Reconcile `docs/` as described above, then run `./awf check`, review the full diff, and run the repository's tests or gate. Commit the author-owned guidance, topics, and generated outputs together.

The fixed outputs are five skills under each of `.agents/skills/` (serving Codex, Pi, and omp) and `.claude/skills/`, the root `awf` wrapper, `.awf/bootstrap.sh`, `.awf/.gitignore`, and `.awf/VERSION`. A leading AWF comment marks each as generated, except `.awf/VERSION`: that exact path is reserved for AWF's renderer-version record and may be replaced without a marker, so move any unrelated content there first. The record is not configuration, a binary pin, or a prerequisite for commands; the bootstrap selects the pinned binary.

Rendering refuses non-regular destinations and unmarked collisions other than `.awf/VERSION`. To give AWF a colliding destination, preserve useful content elsewhere, then remove or move the destination deliberately; do not add an AWF marker to authored content. If generation stops after partial writes, inspect the output and diff, keep valid files, correct the reported problem, and rerun `render`. AWF never deletes retired output automatically.

## Connect checks to automation

Add `./awf check` to the repository's existing gate and CI after checkout. It validates the `docs/` knowledge bundle (including ADR state pairs), topic selectors, generated bytes, executable state, and retired ownership markers in the working tree. It does not validate an isolated staged snapshot, Git history, or project-specific behavior, and does not prove overall integration. Keep source edits, rendering, review, staging, and commits explicit.

An optional repository-owned pre-commit hook can be:

```sh
#!/bin/sh
set -eu
exec ./awf check
```

Make it executable and integrate it into the existing hook dispatcher or configured directory. For a repository deliberately using `.githooks` with no conflicting arrangement:

```sh
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
```

Preserve unrelated hook behavior and existing `core.hooksPath` configuration. The repository owns hooks, CI, gates, commit conventions, and Git configuration; AWF does not install, activate, edit, or remove hooks. The completion workflow (`awf docs completion`) owns the default cadence of agent commits.

## Update the pinned release

Read the target release's guides before changing the pin:

```sh
curl -fsSL https://github.com/hypnotox/agentic-workflows/releases/download/v<target>/awf.sh | bash -s -- docs integration
```

For a compatible update, explicitly select the target binary through the existing wrapper:

```sh
AWF_VERSION=<target> ./awf render
./awf check
```

The target renderer rewrites the committed bootstrap pin and `.awf/VERSION`, which `check` compares for drift. Never silently substitute the latest release. When the target's changelog or `awf docs migrate` describes an incompatible change, follow that guidance instead of assuming render is sufficient.

## Repair and confirm

Use the reported path and diff to distinguish stale marked output (render it), unmarked collisions (reconcile ownership), retired marked files (delete or unmark deliberately), and invalid knowledge metadata, reserved files, or topic selectors (fix their authored source using `awf docs knowledge` and `awf docs topics`). A missing or stale version record is generated drift, repaired by render—not a request to configure AWF. A migration error naming a retired `.awf` location means an older installation remains; see `awf docs migrate`.

For incomplete integration, inspect repository gates, CI, hook scripts, executable modes, and effective hook configuration; AWF does not assess them.
