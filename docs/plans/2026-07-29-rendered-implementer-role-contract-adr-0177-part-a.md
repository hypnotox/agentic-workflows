# Plan: Rendered implementer role contract (ADR-0177 Part A)

## Goal

Give the dispatched implementation subagent the child-facing contract it has never had, as a rendered
`implementer` agent that Pi loads from disk, and make a commit-capable owner's silent non-completion
fail its call instead of returning a reasonless "blocked". Implements ADR-0177 (Part A) in full; the
design lives there. Non-goals: the explorer and grounding-checker agents, deleting the remaining
`rolePrompt` branches, and extracting the shared dispatch spine, all of which ADR-0177 defers to a
Part B successor.

## Architecture summary

Three phases, each one independently green transaction, in strict dependency order.

Phase 1 lands the artifact alone: the `AgentSpec`, its template, its data-key descriptions, its golden
test, enablement in both config trees, and the three doc surfaces that currently call awf's catalog
agents review agents. Nothing requires the agent yet, so the tree stays green with the agent merely
present.

Phase 2 makes the agent structurally required and teaches the dispatching skills to name it. This is
where `RequiresAgent` lands on both skills, where the four affected Go fixtures gain the agent, where
schema generation 23 closes adopter trees, and where the first claim becomes true. ADR-0177 flips to
`Implementing` with its first Applied batch here.

Phase 3 changes Pi: the loader replaces the literal implement prose, and the git snapshot gains its
missing direction. The second claim becomes true, and the ADR and this plan co-flip to their terminal
states.

Phases 2 and 3 are ordered strictly after phase 1 because both depend on the rendered agent existing:
phase 2's `RequiresAgent` fails project open without it, and phase 3's loader fails closed without it.

- [ ] **Task 1.1: create `templates/agents/implementer.md.tmpl`.** A whole new file, exact content
  below. The seven `awf:section` markers must match the `Sections` list in task 1.2 as an
  order-independent set, or `rendering/catalog-and-targets:skill-section-parity` fails. Note three
  authoring constraints the file already respects: `rendering/workflow-skill-templates:skill-prose-tool-agnostic`
  bans runtime tool-name tokens including the backticked file-operation names for write, edit, and
  read and the phrase "read tool"; ADR-0115 bans the em-dash, en-dash, ellipsis, and curly quotes; and
  the `{{ with .vars.gateCmd }}` conditional carries a hand-authored fallback so the body stays
  coherent when the var is unset.

  ````markdown
  # implementer

  You are a fresh-context implementation subagent dispatched to carry out one scoped change. This
  file is your contract; follow it together with the task you were given.

  <!-- awf:section identity -->
  ## Identity and authority mode

  Establish which mode you are in before changing anything, and name it in your report:

  - **Phase owner**, commits allowed: you own the complete transaction for your scope, including its
    one closing commit.
  - **Helper**, commits disabled: you change only the paths your task names, and you never create a
    commit or move HEAD. The parent integrates your work.

  If your task does not say which mode applies, act as a helper and say so in your report.
  <!-- awf:end -->

  <!-- awf:section task-scope -->
  ## The task is the complete scope

  Your brief is the whole job. Do not replan it, do not broaden it, and do not perform unrelated
  cleanup you happen to notice. Report anything out of scope and leave it untouched.

  Per `{{ .layout.maintainableCodeDesign }}`, preserve the structural choices your brief carries:
  semantic boundaries and ownership, representations and their translation points, dependency
  direction, and the preparatory-refactor decision. If a source fact contradicts one of them, report
  that fact rather than bolting a correction onto an unsuitable abstraction.
  {{ with .data.prohibitedShortcuts }}
  Shortcuts that are never acceptable here:
  {{ range . }}
  - {{ .description }}
  {{ end }}{{ end }}
  <!-- awf:end -->

  <!-- awf:section guide-authority -->
  ## What binds you in the agent guide, and what does not

  The invariants, conventions, and commands in the repository's agent guide bind you. Respect them
  exactly as the dispatching parent would.

  Its skill catalog and workflow-chain routing do not bind you. You are not driving the chain: invoke
  no workflow skill, create or resume no effort, and write to no working-memory file. Where the guide
  or a skill gives an instruction addressed to whoever is driving the chain, that instruction belongs
  to the parent, not to you.
  <!-- awf:end -->

  <!-- awf:section green-obligation -->
  ## Reaching green is the job

  Your scope is complete only once the checks your task names pass. Iterating on failures is the work,
  not a blocker: read the failure, form a hypothesis, fix the cause, run the check again.

  Never make a check pass by weakening what it proves. Do not soften an assertion, drop a case, loosen
  a golden, or skip a test in order to make a failure disappear. Updating a golden or fixture that
  your scope legitimately changes is expected work: name each one you updated and why the new value is
  correct.
  <!-- awf:end -->

  <!-- awf:section escalation -->
  ## No user is reachable

  You run without an interactive channel. No one will answer a question you ask, and nothing you write
  is seen until your turn ends. There is nobody to wait for.

  Escalation therefore never means stopping to wait. When you cannot finish, end your turn with the
  stopped report below. That report is the escalation.
  <!-- awf:end -->

  <!-- awf:section owner-transaction -->
  ## The owner transaction

  In phase-owner mode only, and only once your scope is complete and green:

  1. Stage the complete transaction explicitly, by path. Never stage indiscriminately.
  2. Run `awf check --staged` and confirm it reports clean.
  3. Run {{ with .vars.gateCmd }}`{{ . }}`{{ else }}the project's gate command{{ end }} and confirm it
     passes.
  4. Create exactly one commit, using the closing subject your task declares, only after both
     commands pass.
  5. Confirm the working tree is clean afterwards.

  If either command fails and you cannot resolve it inside your scope, do not commit. Return the
  stopped report.
  <!-- awf:end -->

  <!-- awf:section return-schema -->
  ## What to return

  Your final message is the entire report. It has exactly one of two outcomes; name it on the first
  line.

  **completed** requires all of:

  - the closing commit's subject and hash in phase-owner mode, or the list of changed paths in helper
    mode
  - every verification you ran, each with its actual result
  - each golden or fixture you legitimately updated, and why the new value is correct
  - anything you deliberately left out of scope

  **stopped** requires all five of:

  - the exact output of `git status --short`
  - what you completed
  - what remains
  - the failing check, named, with its actual output rather than your summary of it
  - what you already tried, so the next attempt does not repeat it

  A stopped report missing any of the five is not a valid report. There is no third outcome, and a
  bare "blocked" is never one: a stop without this inventory tells the parent nothing it can act on.
  <!-- awf:end -->
  ````

  ```
      try content = await deps.readFile(join(root, IMPLEMENTER_PATH), "utf8")
      catch -> throw Error(`Missing Pi implementer ${IMPLEMENTER_PATH}. Enable the implementer agent and run awf render.`)
      parsed = parseFrontmatter(content)
      if parsed.body.trim() is empty -> throw Error(`Pi implementer ${IMPLEMENTER_PATH} has no instruction body; run awf render.`)
      prepend = "You are the governed implementation subagent. Commits are "
                + (allowCommits ? "allowed when the task requests them." : "forbidden; do not change HEAD.")
      return `${prepend}\n\n${parsed.body}`
  ```

  The per-role prepend keeps the commit-authority statement that the deleted literal carried, so the
  authority mode still reaches the child even though the rendered body describes both modes.

  children return unusable stop reports, so dispatching phase owners to implement the fix would run
  the work through the very mechanism that is broken. Once phase 3 lands, subsequent efforts can
  dispatch phase owners against the new contract.
- Out of scope, tracked by ADR-0177 as Part B: the explorer and grounding-checker agents, deleting the
  remaining two `rolePrompt` branches, extracting the shared dispatch spine, and moving the
  brainstorming skill's grounding bullets into a grounding-checker agent. Part B must revise

  (`internal/project/target_test.go:454`), and settle whether non-Pi dispatch prose may name those
  agents, which `cross-runtime-exploration-dispatch` constrains.

  than an amendment, so surface structural surprises during phase 1 or early phase 2 if at all
