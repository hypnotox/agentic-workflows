# Plan: Establish Publishing Coordinator

## Goal

Establish one application-level Publisher and one semantic publication result model for output planning, rendering coordination, backup decisions, sync, initialization, and sync-time prune while preserving every existing command result, generated byte, atomic publication guarantee, backup rule, partial-result contract, and RF-002 immutable-state boundary. Full uninstall remains resident-owned and unchanged. Do not implement repository-check aggregation, current-state coordination, command-use-case extraction, residual test cleanup, compatibility cleanup, adopter changes, or another audit issue.

## Architecture summary

ADR-0296 supplies the approved owner map and dependency direction. ADR-make-publisher-the-output-plan-construction-owner makes Publisher the sole plan constructor while neutral immutable plan values remain below application coordination. A bounded enabling extraction moves immutable loaded project facts into a lower `internal/projectstate` owner while `internal/project` preserves the RF-002 `ProjectState` compatibility name. Resolved target declarations remain immutable loaded facts there; their output-related fields are data consumed by Publisher, not plan or publication behavior. This breaks the otherwise direct `project -> publisher -> project` cycle without exporting mutable catalogs, adding a publisher-specific dependency bag, or moving application policy into a mechanism.

A concrete `internal/publisher` owner consumes project state plus an explicit operation tree reader. It owns output-plan construction, rendering coordination, backup and sync-time prune decisions, sync and initialization authority, resident-marker rendering, and a semantic `Result` whose owner maps it to central presentation values. Neutral immutable declarations and plan values move to a lower `internal/outputplan` package so residual repository checks, staged checks, and current-state projections can consume one Publisher-produced plan without importing application coordination or reimplementing planning. `cmd/awf` composes Publisher and retains parsing, caller-specific partial-result handling, stream selection, rendering, and exit mapping. Ordinary sync continues to discard a partial result when it returns an error; upgrade continues to preserve the committed partial metadata alongside that error.

`internal/filesystem` retains confinement, Replace, and its backup adapter; `internal/filepublication` remains a transitive atomic no-replace mechanism and Publisher never calls its path APIs directly. `internal/render`, manifest, Git, snapshot, and presentation retain syntax, lock representation, repository, snapshot, and grammar ownership. Full uninstall, including its result and presentation, remains in `internal/resident`; only sync-time prune belongs to Publisher. The extraction removes obsolete project publishing entry points and parallel planning paths in the same phase that their consumers migrate. Publisher Result storage and lower plan/declaration storage are private and exposed through defensive semantic projections. Existing focused publication tests move with their owner; structural caller, import-direction, immutability, single-plan, retained-uninstall, and partial-failure oracles prevent ownership from drifting back.

**Plan flexibility.**

The protected-contract rule in the workflow document governs what a plan may not change. The plan records the best known route at authoring time, not a binding implementation choreography. A commit-capable owner may merge, split, reorder, add, remove, or replace recorded route detail while the protected contract holds. A path omitted from the plan is not alone a reason to stop, and a stale listed path need not be touched. Reapproval is required only when the protected contract would change or an unresolved material decision appears.

Reconcile a Proposed plan only when another phase or reviewer could rely on stale material instructions. Inconsequential and independently local edits require no deviation record. A delegated owner reports material cross-owner revisions for parent reconciliation. A helper remains confined to its assigned paths and gains no scope, commit, review, checkpoint, handoff, or outcome authority from route flexibility.

## Definition of done

- `dod: state-boundary` Immutable loaded state has one lower owner that preserves RF-002 compatibility and supplies no operation dependency, mutable alias, or reverse application edge.
- `dod: single-plan` Every output-plan, rendered-output, drift, tracking, advisory, staged, and context declaration consumer uses one Publisher-produced neutral plan or projection per operation, with no parallel planner or checker-to-Publisher dependency.
- `dod: publisher-owner` One concrete application-level Publisher owns output-plan construction, rendering coordination, backup and sync-time prune decisions, sync, initialization, resident-marker rendering, and its semantic Result; `internal/project` owns none of those responsibilities and `internal/resident` retains full uninstall.
- `dod: publication-evidence` Existing per-file atomic publication, root confinement, collision retry, backup, mode, prune, authority, failure, partial-progress, and lock-advancement behavior remains covered at the owning boundary without duplicated mechanisms.
- `dod: compatibility` CLI results, presentation bytes, streams, exits, ordering, generated paths and bytes, lock semantics, staged isolation, context edges, and ADR-0297 compatibility remain unchanged; focused tests, rendered drift checks, the full 100 percent gate, dead-code and dependency checks, and workflow audits finish clean.
